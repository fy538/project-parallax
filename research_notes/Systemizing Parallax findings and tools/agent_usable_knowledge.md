# Making findings, techniques and small tools reliably usable by Claude Code and Agent SDK agents (state as of 2026-10-11)

Retrieval note. Claude Code documentation pages (code.claude.com/docs) were retrieved on 2026-10-11; they carry no publication date and reference CLI versions up to v2.1.295. "Official" below means Anthropic documentation or Anthropic-authored posts; everything else is labelled third-party. Measurements of the project-parallax repo (taken 2026-10-11 with `wc` and a frontmatter parse) are not web-sourced and therefore appear only under Inferences. Quotation marks reproduce text as returned by the page-fetch tool; for long pages that tool relays excerpts through a summarizing model, so any quotation destined for publication should be spot-checked against the linked page. Paraphrases are left unquoted.

## 1. Mechanisms and their intended use

### Takeaway
Anthropic's documentation draws one line through all the mechanisms: what loads into every request (CLAUDE.md, unscoped rules, output style, skill descriptions) should be small and factual; what is procedural or reference goes into skills and their files (loaded on demand); what must happen every time goes into hooks, permissions, lints or scripts (deterministic, zero context cost). The documented numeric targets are: CLAUDE.md under 200 lines, SKILL.md under 500 lines (spec: under 5,000 tokens), skill description at most 1,024 characters (spec) and at most 1,536 characters in Claude Code's listing, with the whole skill listing held to 1% of the context window.

### Cited Findings

**CLAUDE.md, rules, AGENTS.md (official)**
- Purpose: "Keep it to facts Claude should hold in every session: build commands, conventions, project layout, 'always do X' rules. If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule instead." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Size: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." A file up to 4 MiB still loads in full; larger is skipped. A warning appears at startup and in `/status` when a file is over the recommended length or when files together pass a combined limit (the numeric thresholds are not stated). — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Imports: `@path/to/file`, recursive to "a maximum depth of four hops"; imports "help you organize a long file but don't reduce its context cost, because imported files also load at launch." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Load order: files in the working directory and every ancestor load at launch and are concatenated (root first, working directory last; `CLAUDE.local.md` after `CLAUDE.md`). Subdirectory CLAUDE.md files load only "once Claude reads, writes, or edits another file in that subdirectory." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Block-level HTML comments in CLAUDE.md are stripped before injection, so maintainer notes cost no tokens. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Enforcement status: "CLAUDE.md content is delivered as a user message after the system prompt... there's no guarantee of strict compliance, especially for vague or conflicting instructions." "If two instructions contradict each other, Claude may pick one arbitrarily." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Compaction: project-root CLAUDE.md is re-read from disk and re-injected after `/compact`; nested files and path-scoped rules only reload on demand. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- `.claude/rules/*.md`: one topic per file; a rule without `paths` frontmatter loads at launch with the same priority as `.claude/CLAUDE.md`; a rule with `paths` globs loads only when Claude reads, writes or edits a matching file. `paths` is the only frontmatter field read. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Built-in audits: `/doctor prompt-audit` (v2.1.283+) checks CLAUDE.md, AGENTS.md, rules, skills, commands, subagents and output styles for "instructions written for older models, references to files or commands that don't exist, and files that contradict each other"; `/doctor` (v2.1.206+) proposes trims that cut "content Claude can derive from the codebase, such as directory layouts, dependency lists, and architecture overviews" and keep "pitfalls, rationale, and conventions that differ from tool defaults." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- AGENTS.md: read directly since v2.1.277, but by default only when no `CLAUDE.md`/`CLAUDE.local.md` exists in the working directory or above. When both exist Claude reads the CLAUDE.md files only, unless Project instructions is set to `claude-md-and-agents-md` or CLAUDE.md contains an `@AGENTS.md` import. "A CLAUDE.md that tells Claude in words to read AGENTS.md: Claude sees AGENTS.md only if it decides to open the file." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- AGENTS.md (third-party spec site): "a README for agents", plain Markdown with no required fields, stewarded by the Agentic AI Foundation under the Linux Foundation, "used by over 60k open-source projects"; nested files allowed and "the closest AGENTS.md to the edited file wins"; no size guidance given; Claude Code is not in the site's supporter list. — [agents.md](https://agents.md/)

**Auto memory directory (official)**
- Location `~/.claude/projects/<project>/memory/`, with a `MEMORY.md` index ("one line per memory") plus one topic file per memory. "The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation"; topic files are read on demand. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Four memory types recorded in frontmatter: `user`, `feedback`, `project` ("ongoing work, deadlines, and decisions that Claude can't derive from the code or git history"), `reference` ("where to find information outside the project"). "Claude skips anything it can derive from the codebase... It also skips anything your CLAUDE.md files already say." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Machine-local, shared across worktrees of one repo, not loaded into subagents (forks excepted); a `modified` ISO timestamp is written on each save (v2.1.214+). Saying "remember X" writes to auto memory; "add this to CLAUDE.md" writes to CLAUDE.md. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)

**Skills and slash commands (official)**
- "Unlike CLAUDE.md content, a skill's body loads only when it's used, so long reference material costs almost nothing until you need it." Create one "when a section of CLAUDE.md has grown into a procedure rather than a fact." Custom commands are merged into skills: `.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` "both create /deploy and work the same way." — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- Locations: enterprise, `~/.claude/skills/`, `.claude/skills/`, nested `<subdir>/.claude/skills/` (loaded the first time Claude touches a file in that subdirectory), plugins (namespaced `/plugin:skill`). Name clashes resolve enterprise over personal over project. — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- Frontmatter Claude Code acts on includes `description`, `when_to_use`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork` + `agent`, `paths` (globs limiting automatic activation), `hooks` (registered on invocation, kept for the session), `arguments`/`argument-hint`. Unknown fields are ignored silently in Claude Code, but on claude.ai uploads and the Skills API anything beyond `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools` is "a hard error." — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- Triggering: names and descriptions are listed in context; "Claude matches your task against skill descriptions to decide which are relevant. If descriptions are vague or overlap, Claude may load the wrong skill or miss one that would help." — [Claude Code docs: features overview](https://code.claude.com/docs/en/features-overview)
- Listing budget: "The budget scales at 1% of the model's context window. When the listing overflows, Claude Code drops descriptions starting with the skills you invoke least." Every name stays listed. Each entry's `description` + `when_to_use` is capped at 1,536 characters ("put the key use case first"). Controls: `skillListingBudgetFraction`, `SLASH_COMMAND_TOOL_CHAR_BUDGET`, `skillListingMaxDescChars`, and `skillOverrides` values `on` / `name-only` / `user-invocable-only` / `off`. `disable-model-invocation: true` keeps a description out of context entirely. — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- Size: "Keep SKILL.md under 500 lines. Move detailed reference material to separate files." "Once a skill loads, its content stays in context across turns, so every line is a recurring token cost." — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- Lifecycle: invoked content "enters the conversation as a single message and stays there"; the file is not re-read. After auto-compaction Claude Code re-attaches "the most recent invocation of each skill... keeping the first 5,000 tokens of each" within "a combined budget of 25,000 tokens." The skill listing itself is not re-injected after `/compact`. — [Claude Code docs: skills](https://code.claude.com/docs/en/skills); [Claude Code docs: context window](https://code.claude.com/docs/en/context-window)
- Two content types: reference content (conventions, style guides; runs inline) and task content (step-by-step actions, often with `disable-model-invocation: true`). "`context: fork` only makes sense for skills with explicit instructions"; a guidelines-only skill forked into a subagent "returns without meaningful output." — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- Open spec limits: `name` 1–64 chars, lowercase/digits/hyphens, must match directory; `description` 1–1,024 chars; `compatibility` up to 500 chars; `allowed-tools` experimental. Progressive disclosure tiers: metadata (~100 tokens), instructions ("< 5000 tokens recommended"), resources as needed. "Keep file references one level deep from SKILL.md." Validate with `skills-ref validate`. — [Agent Skills specification](https://agentskills.io/specification)
- The format "was originally developed by Anthropic, released as an open standard"; the client list as retrieved includes Claude Code, Claude, ChatGPT and Codex, Cursor, Gemini CLI, GitHub Copilot, VS Code, Goose, OpenCode, Amp and Junie, out of roughly 45 listed clients. — [agentskills.io](https://agentskills.io/home)

**Plugins (official)**
- "Plugins are the packaging layer"; trigger for adopting one: "A second repository needs the same setup." — [Claude Code docs: features overview](https://code.claude.com/docs/en/features-overview)
- `claude plugin details <name>` prints projected always-on and on-invoke token cost per component; the marketplace highlights an always-on cost of 2,000 tokens or more; a plugin is flagged "Not used recently" after 14 days and 10 sessions unused. — [Claude Code docs: measure plugin cost](https://code.claude.com/docs/en/plugins/measure)

**Subagents (official)**
- Use a subagent when a side task would flood the main context with output that will not be referenced again, or when the same kind of worker keeps being spawned with the same instructions. Defined in `.claude/agents/`; delegation is driven by the `description` ("use proactively" encourages it); a startup warning appears when custom agent descriptions exceed 15,000 tokens combined. — [Claude Code docs: sub-agents](https://code.claude.com/docs/en/sub-agents)
- A non-fork subagent gets its own system prompt, the delegation message, CLAUDE.md (unless `omitClaudeMd` or Explore/Plan), and the full content of skills in its `skills:` field. It does not get conversation history, already-invoked skills, the output style, or the main auto memory; rules that must reach the subagent have to be restated in the delegation prompt. Optional persistent `memory: user|project|local` gives it its own MEMORY.md (same 200-line/25KB limit). — [Claude Code docs: sub-agents](https://code.claude.com/docs/en/sub-agents)

**Hooks (official)**
- "Hooks are user-defined shell commands... which gives you deterministic control: certain actions always happen rather than relying on the LLM to choose to run them." Types: `command`, `http`, `mcp_tool` (deterministic) and `prompt`, `agent` (model judgment; agent hooks "experimental"). Exit code 2 blocks the action and feeds stderr back. Events include SessionStart (sources `startup|resume|clear|compact|fork`), UserPromptSubmit, PreToolUse, PostToolUse, Stop, PreCompact/PostCompact, InstructionsLoaded. A documented recipe re-injects critical context with a `SessionStart` hook and `compact` matcher. — [Claude Code docs: hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Context cost: "Zero, unless the hook returns output." "If a rule must hold every time, make it a hook rather than a prompt instruction." — [Claude Code docs: features overview](https://code.claude.com/docs/en/features-overview)

**MCP servers (official)**
- For "external data or actions"; trigger: "You keep copying data from a browser tab Claude can't see." "MCP gives Claude purpose-built tools for an external system... Skills give Claude knowledge about how to use those tools effectively." — [Claude Code docs: features overview](https://code.claude.com/docs/en/features-overview)
- Tool search is on by default: only tool names and server instructions load at start, schemas are deferred. Tool descriptions and server instructions are truncated at 2,048 characters. Output: warning above 10,000 tokens, default cap 25,000 tokens (`MAX_MCP_OUTPUT_TOKENS`), text results over 50,000 characters are saved to a file. A server can force a human approval on every call with `_meta["anthropic/requiresUserInteraction"]: true`. — [Claude Code docs: MCP](https://code.claude.com/docs/en/mcp)

**Output styles (official)**
- "An output style is a set of instructions that sets Claude's role, tone, and response format for every response in a session." Stored in `~/.claude/output-styles` or `.claude/output-styles`; one active at a time; a custom style drops Claude Code's software-engineering instructions unless `keep-coding-instructions: true`. Not for project facts (CLAUDE.md) or guarantees (hooks). — [Claude Code docs: output styles](https://code.claude.com/docs/en/output-styles)
- Output styles carry the highest instruction-following weight of the file-based methods and "should be used judiciously." — [Anthropic blog, "Steering Claude Code", Michael Segner, 2026-06-18](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)

**Context cost summary (official)**
- CLAUDE.md: full content, every request. Output style: full, every request. Skills: descriptions at start, body when used. MCP: tool names at start, schemas on demand. Subagents: isolated. Hooks: zero unless they return output. — [Claude Code docs: features overview](https://code.claude.com/docs/en/features-overview)
- The docs' simulated session shows a ~4,200-token system prompt, ~1,800-token project CLAUDE.md, ~450 tokens of skill descriptions and ~680 tokens of MEMORY.md as an illustrative startup. — [Claude Code docs: context window](https://code.claude.com/docs/en/context-window)

**Agent SDK (official)**
- Omitting `settingSources` makes `query()` read the same filesystem settings as the CLI (user, project, local: CLAUDE.md, rules, skills, agents, commands, hooks); `settingSources: []` disables them. Auto memory and `~/.claude.json` load regardless. "Skills must be created as filesystem artifacts... The SDK does not have a programmatic API for registering skills." Hooks can also be programmatic callbacks; MCP servers via `mcpServers`; subagents via `agents`. — [Agent SDK docs: Claude Code features](https://code.claude.com/docs/en/agent-sdk/claude-code-features)

### Inferences
- Local measurement: `/Users/feihuyan/project-parallax/CLAUDE.md` is 180 lines but 42,478 bytes (very long lines; on the order of 10K tokens at ~4 chars/token, versus the ~1,800 tokens the docs use as an illustrative project file). It passes the 200-line target by count while failing its intent. The "Shipped May..." changelog sections are the kind of content the `/doctor` trim removes (derivable from code and git history).
- Local measurement: CLAUDE.md tells Claude in words to "read AGENTS.md first" (341 lines, 59,309 bytes). Per the docs, with a CLAUDE.md present AGENTS.md is not auto-loaded and is seen only if the agent chooses to open it. Converting that sentence to an `@AGENTS.md` import would load 59KB into every request, so the better fix is to shrink both, not to import.
- Local measurement: 25 project skills in `.claude/skills/` (mirrored in `skills/`); descriptions total about 19,300 characters (mean ~770). Four exceed the spec's 1,024-character limit (`timeline-audit` 1,276; `typography-audit` 1,070; `map-audit` 1,069; `diagram-audit` 1,042). If the listing budget is 1% of a 200K-token window (about 2,000 tokens, roughly 8,000 characters by my arithmetic; the docs do not give the character conversion), the project's descriptions alone overflow it, before counting synced and bundled skills. In the skill listing delivered to this research session, `typography-audit` and several synced skills appeared name-only, which is consistent with (not proof of) budget-driven description dropping. `/doctor` and `/skill-doctor` will confirm.
- Local measurement: three SKILL.md files exceed the 500-line guidance (`visual-spec` 1,013 lines, `publish-retro` 730, `render-qa` 568). After compaction only the first 5,000 tokens of each invoked skill are restored, so the tail of `visual-spec` is the part most likely to be silently lost in a long session.
- For a solo, single-repo pipeline, plugins add packaging overhead without a second repository to justify them; the exception is `claude plugin eval`, which requires a plugin or "skills-directory plugin" layout (see section 6).
- Output styles are a weak fit here: the project's voice doctrine applies to scripts being written, not to every agent response, so it belongs in the script skills.

### Gaps
- The numeric thresholds behind the "over the recommended length" and "combined limit" startup warnings are not stated in the docs.
- The docs state the skill listing budget as "1% of the model's context window" but not in characters, nor whether a floor applies on 200K-context models.
- Subagent nesting depth conflicts between sources: the sub-agents doc page (retrieved 2026-10-11) says three layers below the main conversation by default; the June 2026 Anthropic blog says five. Not resolved.
- I could not confirm from a dated source when the SDK's default for `settingSources` became "load everything"; older SDK material may describe the opposite default, so check the installed SDK version.

## 2. Skill design

### Takeaway
Anthropic's guidance is consistent across three sources (platform best practices, agentskills.io, the skill-creator skill): a skill is one coherent unit of work, its description is a trigger condition, its SKILL.md is a short navigation layer, and bulk (reference, data, scripts) sits one level below with an explicit statement of when to open each file. For a large catalogue the documented pattern is many domain-split files plus an index and grep hints, with deterministic work pushed into scripts; no official source recommends one giant file.

### Cited Findings

**Scope**
- "Deciding what a skill should cover is like deciding what a function should do... Skills scoped too narrowly force multiple skills to load for a single task, risking overhead and conflicting instructions. Skills scoped too broadly become hard to activate precisely." — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- "Overly comprehensive skills can hurt more than they help — the agent struggles to extract what's relevant and may pursue unproductive paths triggered by instructions that don't apply to the current task. Concise, stepwise guidance with a working example tends to outperform exhaustive documentation." — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Anthropic's Claude Code team found their skills cluster into nine recurring categories (library/API reference, product verification, data fetching, business automation, scaffolding, code quality/review, CI/CD, runbooks, infrastructure ops); the best skills fit one category cleanly. — [Thariq Shihipar (Anthropic), 2026-03-17, third-party mirror of the X post](https://gist.github.com/Danm72/467f6d6cd193d19c0042371866d53b75)
- Measured (third-party research): across 87 tasks and 18 model-harness configurations, curated skills raised average pass rate from 33.9% to 50.5% (+16.6 points; range +4.1 to +25.7 by configuration), and focused skills with at most three modules outperformed larger or exhaustive bundles. — [SkillsBench, arXiv 2602.12670, v4 2026-06-14](https://arxiv.org/abs/2602.12670)

**Descriptions**
- Limits: 64-char name, 1,024-char description; "Always write in third person. The description is injected into the system prompt"; include "both what the Skill does and specific triggers/contexts for when to use it"; Claude picks "from potentially 100+ available Skills." — [Anthropic platform docs: skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Use imperative phrasing... 'Use this skill when...'"; "Focus on user intent, not implementation"; "Err on the side of being pushy"; "Keep it concise. A few sentences to a short paragraph." — [agentskills.io optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)
- Claude "has a tendency to 'undertrigger' skills", so descriptions should be "a little bit 'pushy'." — [anthropics/skills skill-creator SKILL.md](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- "Agents typically only consult skills for tasks that require knowledge or capabilities beyond what they can handle alone. A simple, one-step request... may not trigger a PDF skill even if the description matches perfectly." — [agentskills.io optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)
- "The description field is for the model": a trigger condition, "not a summary." — [Thariq Shihipar, mirror](https://gist.github.com/Danm72/467f6d6cd193d19c0042371866d53b75)

**SKILL.md body and reference files**
- "The context window is a public good." "Default assumption: Claude is already very smart. Only add context Claude doesn't already have." "Keep SKILL.md body under 500 lines for optimal performance." — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "SKILL.md serves as an overview that points Claude to detailed materials as needed, like a table of contents in an onboarding guide." "Keep references one level deep from SKILL.md" because with nested references Claude "might use commands like `head -100` to preview content rather than reading entire files." "For reference files longer than 100 lines, include a table of contents at the top." — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- skill-creator sets the table-of-contents threshold at 300 lines and says to organize by variant (separate aws/gcp/azure files, Claude reads only the relevant one). — [anthropics/skills skill-creator SKILL.md](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- "The key is telling the agent *when* to load each file. 'Read `references/api-errors.md` if the API returns a non-200 status code' is more useful than a generic 'see references/ for details.'" — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Gotchas: "The highest-value content in many skills is a list of gotchas"; keep them in SKILL.md because for non-obvious issues "the agent may not recognize the trigger" to open a separate file; "When an agent makes a mistake you have to correct, add the correction to the gotchas section." — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Degrees of freedom: text instructions where "multiple approaches are valid"; exact scripts where "operations are fragile and error-prone" ("Run exactly this script... Do not modify the command"). "Provide defaults, not menus." "Favor procedures over declarations." — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Tone: explain why "in lieu of heavy-handed musty MUSTs"; all-caps ALWAYS/NEVER is a warning sign. agentskills.io agrees: "Reasoning-based instructions... work better than rigid directives." — [skill-creator SKILL.md](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md); [agentskills.io evaluating skills](https://agentskills.io/skill-creation/evaluating-skills)
- "Avoid time-sensitive information"; keep superseded methods in a collapsed "Old patterns" section. "Use consistent terminology." — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

**Large reference catalogues**
- Pattern 2, domain-specific organization: one reference file per domain, SKILL.md lists them with one-line scopes and gives grep commands ("Find specific metrics using grep: `grep -i "revenue" reference/finance.md`"). — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Bundle comprehensive resources: Include complete API docs, extensive examples, large datasets; no context penalty until accessed." "Name files descriptively." — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- The spec reserves `assets/` for "Data files (lookup tables, schemas)" and says of `references/`: "Keep individual reference files focused. Agents load these on demand, so smaller files mean less use of context." — [Agent Skills specification](https://agentskills.io/specification)
- Scripts instead of reading: "Utility scripts can be executed through bash without loading their full contents into context. Only the script's output consumes tokens." "Prefer scripts for deterministic operations." — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- The amount of context a skill can bundle is "effectively unbounded" because files load only as needed. — [Anthropic engineering, "Equipping agents for the real world with Agent Skills", 2025-10-16, updated 2025-12-18](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)

**Tables, templates, choosers**
- Templates: "more reliable than describing the format in prose, because agents pattern-match well against concrete structures." — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Conditional workflow pattern ("Guide Claude through decision points": "Creating new content? → Follow Creation workflow"), with the tip to push large workflows into separate files chosen by task. — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Avoid offering too many options... Provide a default (with escape hatch)." — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- For CLAUDE.md: "group related instructions under markdown headers and bullets. Organized sections are easier for Claude to follow than dense paragraphs." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- On examples: curate "a set of diverse, canonical examples"; of stuffing "a laundry list of edge cases into a prompt" the post says: "We do not recommend this." — [Anthropic engineering, "Effective context engineering for AI agents", 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**Scripts, evaluation, iteration** (detail in sections 4 and 6)
- "Create evaluations BEFORE writing extensive documentation"; three scenarios; iterate with "Claude A" (author) and "Claude B" (fresh user of the skill); watch for "ignored content" and "overreliance on certain sections." — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Even a single pass of execute-then-revise noticeably improves quality." — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)

### Inferences
- A 70-entry technique catalogue should not be a SKILL.md body. The documented shape is: a short skill (when to consult the catalogue, the chooser, the gotchas) plus either one reference file per technique family with a table of contents, or a structured data file queried by a script. Since SkillsBench found skills with at most three modules outperform exhaustive bundles, the family split should be coarse (a handful of files), not one file per technique that the agent must browse.
- A chooser is supported by the docs when it resolves to a default ("use X; if condition, use Y"), which matches "defaults, not menus." A flat menu of 70 equal options is the documented anti-pattern.
- The description-style advice conflicts on voice (third person versus imperative) but agrees on content: lead with when to use, name the user intent, stay well under 1,024 characters. In Claude Code the binding constraint is the shared listing budget, so shorter descriptions across all 25 skills protect each other.
- The project's existing audit skills (chart, diagram, map, timeline, typography) share a family and near-identical trigger language; the overlap warning in the docs applies. One "template-audit" skill with per-family reference files, or `paths`-scoped activation, would follow the "coherent unit" guidance. This is an inference from the guidance, not a tested result.

### Gaps
- No official guidance found on tables versus prose inside skills beyond the template, checklist and conditional-workflow patterns.
- No official statement on a maximum number of skills; the only hard figures are the listing budget and "100+ available Skills" as a scale the description must work at.
- The SkillsBench abstract as retrieved did not report a result on self-generated skills; I could not confirm that finding.

## 3. Structured knowledge for agents

### Takeaway
The official and practitioner sources converge on a three-way split: prose for judgment and rationale, structured data for facts that are looked up, code (lint, schema, hook, script) for anything that must hold every time. Direct measurement of prose versus JSON/YAML for agent knowledge files is thin; the strongest evidence is for the placement and size of context (small index plus retrievable files) and for deterministic enforcement over instruction. For a few hundred entries, the documented retrieval method is file layout plus grep or a query script; no source reviewed recommends embeddings at that scale.

### Cited Findings
- Official: "If the instruction is something that must run at a specific point, such as before every commit or after each file edit, write it as a hook instead." CLAUDE.md fix for over-specification: "If Claude already does something correctly without the instruction, delete it or convert it to a hook." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory); [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- Official: "A real guardrail needs to be deterministic, and the enforcement methods are hooks and permissions." "The model choosing to run a formatter is different from the formatter running automatically." — [Anthropic blog, "Steering Claude Code", 2026-06-18](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Official: skills can make a rule deterministic too: "sorting via token generation is far more expensive than simply running a sorting algorithm" and "many applications require the deterministic reliability that only code can provide." — [Anthropic engineering, Agent Skills post, 2025-10-16](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Official: plan-validate-execute: have the agent write a structured plan file, then "validate it against a source of truth" with a script whose errors name the valid options ("Field 'signature_date' not found — available fields: ..."). — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Official: verification as the main lever: "Give Claude a check it can run: tests, a build, a screenshot to compare"; the check can be "a linter, a script that diffs output against a fixture"; a Stop hook can block the turn from ending until it passes. — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- Official: what to keep out of prose: exclude "anything Claude can figure out by reading code", "information that changes frequently", "file-by-file descriptions of the codebase"; link to docs instead of copying API detail. — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- Official, retrieval: Claude Code uses a hybrid, with CLAUDE.md loaded up front and "glob and grep" used to "retrieve files just-in-time"; folder hierarchies, naming conventions and timestamps act as signals. Embedding-based retrieval is described as the pre-inference alternative, not as the recommendation for coding agents. — [Anthropic engineering, context engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Official, tool outputs: natural-language identifiers beat opaque IDs ("significantly improves Claude's precision in retrieval tasks by reducing hallucinations"); response structure (XML, JSON, Markdown) affects performance and should be chosen by evaluation. — [Anthropic engineering, "Writing effective tools for agents", 2025-09-11](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Third-party, practitioner: "Never send an LLM to do a linter's job"; use formatters, linters and a Stop hook that returns errors to Claude. "Prefer pointers to copies": avoid code snippets in instruction files because they go stale; use `file:line` references. — [HumanLayer, "Writing a good CLAUDE.md", Kyle, 2025-11-25](https://www.humanlayer.dev/blog/writing-a-good-claude-md)
- Third-party, measured: for Next.js 16 APIs absent from training data, a docs index embedded in AGENTS.md scored 100% on Vercel's evals versus 53% baseline, 53% with a skill (default), 79% with a skill plus explicit instructions. The index was compressed from ~40KB to 8KB with no loss, in a pipe-delimited path-to-files format, plus the instruction "Prefer retrieval-led reasoning over pre-training-led reasoning." The index points to files the agent then reads. — [Vercel blog, Jude Gao, 2026-01-27](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- Third-party, generated docs from data: Vercel's react-best-practices skill keeps one rule per file in `rules/` with frontmatter (`title`, `impact`, `tags`), infers section from filename prefix, and runs `pnpm build` ("Compile rules into AGENTS.md"), `pnpm validate` and `pnpm extract-tests` ("Extract test cases for LLM evaluation"); AGENTS.md is marked generated. — [vercel-labs/agent-skills, react-best-practices](https://github.com/vercel-labs/agent-skills/tree/main/skills/react-best-practices)
- Third-party, reported via secondary summaries only (the original returned HTTP 403 to my fetch): OpenAI's "Harness engineering" post (Ryan Lopopolo, 2026-02-11) is summarized as abandoning one large AGENTS.md in favour of a short AGENTS.md used as a table of contents into a structured `docs/` directory, with constraints "enforced mechanically via custom linters and structural tests." — [OpenAI, original](https://openai.com/index/harness-engineering/); [secondary summary](https://rywalker.com/research/openai-harness); [secondary summary](https://codenote.net/en/posts/harness-engineering-ai-agent-era/)
- Research on format: rendering the same content as plain text, Markdown, JSON or YAML changed GPT-3.5-turbo performance by up to 40% on a code translation task, while larger models (GPT-4) were more robust; the authors conclude no fixed template is best. Not tested on Claude or on agent knowledge files. — [He et al., arXiv 2411.10541, 2024-11-15](https://arxiv.org/abs/2411.10541)

### Inferences
- Decision rule consistent with all sources: if a violation can be detected mechanically (palette hex not in palette.json, an enum value, a missing sidecar file, a deprecated transition name), it should be a lint, schema constraint or hook, and the prose should shrink to one line naming the check. If applying the rule needs judgment about the picture or the argument, it stays prose, with the reason attached. The project already works this way for palette.json, the concept registry (JSON plus schema plus pre-commit validate plus lookup CLI) and the `M-*` manifest lints.
- For the ~70-technique catalogue, the pattern with the most support is the project's own concept-registry pattern: a structured file with a schema as single source of truth, a small query CLI (`search`, `show <id>`, filter by need), a generated human-readable doc, and a skill that says when to query. Vercel's rules-to-AGENTS.md build is a public precedent for generating the readable doc from the data; the Anthropic bigquery example is the precedent for grep-style lookup.
- Vercel's result suggests one always-loaded element is worth having: a compact index (names and one-line "use when" of the technique families, a few hundred tokens) in always-loaded context, because skills go uninvoked when the agent does not realise it should look. It argues against relying on a skill description alone for knowledge the agent must consult unprompted.
- Embeddings or an MCP retrieval server are not justified by any source at a scale of a few hundred entries in a local repo; grep over well-named files or a script over JSON has no index to go stale.
- "Executable documentation" as a named practice was not found in Anthropic material; the equivalent official concepts are verification checks, hooks, validation scripts and plan-validate-execute.

### Gaps
- No controlled study found comparing prose, YAML/JSON and typed code as the home of the same rule for Claude Code specifically.
- OpenAI's harness-engineering details (linter error messages that carry remediation text, doc-gardening agents, "golden principles") could not be verified against the primary text.
- No public measurement found for retrieval approaches (grep versus index file versus embeddings versus MCP) on catalogues of 50–500 entries.

## 4. Tools for agents

### Takeaway
Anthropic's tool guidance is: few, workflow-shaped tools; unambiguous names and parameters; outputs that are short, high-signal and paginated; errors that say what to do next; and evaluation on realistic tasks. For a local repo, Anthropic's own docs call CLI tools "the most context-efficient way to interact with external services," and the skills guidance covers script design (no prompts, `--help`, structured stdout, `--dry-run`, confirmation flags). An MCP server earns its place for systems Claude cannot otherwise reach, or when a human approval must be forced on every call.

### Cited Findings

**Tool design (official)**
- Start simple: "finding the simplest solution possible, and only increasing complexity when needed." Tool interface advice: "Put yourself in the model's shoes"; write descriptions like "a great docstring for a junior developer"; "Poka-yoke your tools. Change the arguments so that it is harder to make mistakes" (example: requiring absolute file paths); the team "spent more time optimizing our tools than the overall prompt." — [Anthropic engineering, "Building effective agents", 2024-12-19](https://www.anthropic.com/engineering/building-effective-agents)
- Choose few tools for high-impact workflows, not one per API endpoint; consolidate chained steps (`schedule_event` instead of list users + list events + create event); overlapping tools distract. Namespace by service and resource; unambiguous parameters (`user_id`, not `user`). — [Anthropic engineering, "Writing effective tools for agents", 2025-09-11](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Return high-signal fields; offer a `response_format` enum (`concise`/`detailed`; the example was 72 versus 206 tokens); paginate, filter, truncate with sensible defaults; "For Claude Code, we restrict tool responses to 25,000 tokens by default"; error responses should give specific, actionable fixes, not codes or tracebacks. — [Anthropic engineering, "Writing effective tools for agents", 2025-09-11](https://www.anthropic.com/engineering/writing-tools-for-agents)
- "One of the most common failure modes we see is bloated tool sets"; "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." — [Anthropic engineering, context engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**Script versus MCP (official and third-party)**
- "CLI tools are the most context-efficient way to interact with external services." "Claude is also effective at learning CLI tools it doesn't already know. Try prompts like `Use 'foo-cli-tool --help' to learn about foo tool`." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- Pre-made scripts are "more reliable than generated code", "save tokens (no need to include code in context)" and "ensure consistency across uses"; state whether to execute or read a script. — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Code execution in place of direct MCP tool calls cut one workflow "from 150,000 tokens to 2,000 tokens" (98.7%) by loading tool definitions on demand and filtering data before it reaches the model; saved working code plus a SKILL.md becomes a reusable skill. The trade-off is sandboxing and operational overhead. — [Anthropic engineering, "Code execution with MCP", 2025-11-04](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Third-party: "almost everything I might achieve with an MCP can be handled by a CLI tool instead"; "LLMs know how to call `cli-tool --help`"; each skill costs "a few dozen extra tokens" whereas "GitHub's official MCP on its own famously consumes tens of thousands of tokens." (Written before MCP tool search became the Claude Code default.) — [Simon Willison, 2025-10-16](https://simonwillison.net/2025/Oct/16/claude-skills/)
- MCP is the documented choice when "you keep copying data from a browser tab Claude can't see." — [Claude Code docs: features overview](https://code.claude.com/docs/en/features-overview)

**Designing scripts an agent runs (official)**
- "Avoid interactive prompts. This is a hard requirement... A script that blocks on interactive input will hang indefinitely." "`--help` output is the primary way an agent learns your script's interface... Keep it concise." Errors should "say what went wrong, what was expected, and what to try." Structured output (JSON/CSV) on stdout, diagnostics on stderr. — [agentskills.io using scripts](https://agentskills.io/skill-creation/using-scripts)
- "Idempotency. Agents may retry commands." "Dry-run support. For destructive or stateful operations, a `--dry-run` flag lets the agent preview what will happen." "Safe defaults. Consider whether destructive operations should require explicit confirmation flags (`--confirm`, `--force`)." "Meaningful exit codes." "Predictable output size. Many agent harnesses automatically truncate tool output beyond a threshold (e.g., 10-30K characters)"; default to a summary and support `--offset` or `--output`. — [agentskills.io using scripts](https://agentskills.io/skill-creation/using-scripts)
- "Solve, don't defer": scripts should handle error conditions themselves; no "voodoo constants." Self-contained dependencies via PEP 723 and `uv run`. — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [agentskills.io using scripts](https://agentskills.io/skill-creation/using-scripts)

**Guarding paid or side-effecting calls (official)**
- "Use `disable-model-invocation: true` for skills with side effects. This saves context and ensures they run only when you name them." — [Claude Code docs: features overview](https://code.claude.com/docs/en/features-overview)
- `allowed-tools` in a skill pre-approves listed tools only "during the turn that invokes the skill"; it does not restrict tools. — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- A `PreToolUse` hook can inspect a tool call and block it with exit code 2; an `if` field filters by tool and arguments using permission-rule syntax (for example `Bash(git *)`). — [Claude Code docs: hooks guide](https://code.claude.com/docs/en/hooks-guide)
- An MCP tool marked `anthropic/requiresUserInteraction: true` prompts on every call, even in `acceptEdits`, `auto` and `bypassPermissions` modes, with no "don't ask again." — [Claude Code docs: MCP](https://code.claude.com/docs/en/mcp)
- Skills can register "on-demand hooks" active only after the skill is invoked (for example a careful mode that blocks destructive commands), and can keep logs or data so later runs build on earlier ones. — [Thariq Shihipar, mirror](https://gist.github.com/Danm72/467f6d6cd193d19c0042371866d53b75)

**Image and video generation inside agent workflows (third-party)**
- fal's hosted MCP server (`https://mcp.fal.ai/mcp`, bearer key per request) exposes nine tools: `search_models`, `get_model_schema`, `get_pricing`, `search_docs`, `run_model`, `submit_job`, `check_job`, `upload_file`, `recommend_model`. Long jobs (video, 3D, training) go through `submit_job` and `check_job`; pricing is a separate lookup. — [fal blog, Lovis Odin, 2026-03-19](https://blog.fal.ai/connect-your-ai-to-1-000-models-with-the-fal-mcp-server)
- A community fal MCP server (raveenb/fal-mcp-server) installs as a Claude Code plugin, expects `FAL_KEY`, saves outputs under `~/Downloads/fal-ai/` by type, and notes video and music generation can take several minutes. Maintenance status varies across community servers. — [Glama listing](https://glama.ai/mcp/servers/raveenb/fal-mcp-server)

### Inferences
- For a fixed handful of fal.ai calls with house prompting rules, repo scripts fit the guidance better than fal's general MCP server: the scripts encode the project's model choice, prompt structure, output location and sidecar record, where the MCP server exposes 1,000+ models and leaves those choices to the agent each time ("bloated tool sets"). The MCP server is useful for exploration of new models, not for the production path.
- The official script checklist maps directly onto a paid-API wrapper: no interactive prompts; `--dry-run` that prints the resolved request and the estimated cost without calling; an explicit `--confirm` (or a spend ceiling flag) for the paid call; idempotent output naming so a retry does not pay twice; JSON on stdout with output path, model, seed, duration and cost; a non-zero, documented exit code per failure class. The project's `tools/ai-video/fal_i2v.py` already writes a JSON sidecar with prompt and cost, which no source reviewed describes but which satisfies the "store data so later runs build on earlier ones" advice.
- Three layers of protection are available without MCP: the skill that wraps generation set to `disable-model-invocation: true`; a `PreToolUse` hook with an `if` pattern on the generation script that blocks unless a confirm flag is present; and a permission rule that does not pre-approve the script.
- Because long video jobs take minutes, the submit/poll split used by fal's MCP (`submit_job`, `check_job`) is the shape to copy in scripts: return a job id immediately and provide a status command, so the agent's turn does not block and output stays small.

### Gaps
- No Anthropic guidance found that specifically covers cost reporting, spend ceilings or sidecar records for paid third-party APIs; the above is assembled from general script, hook and permission guidance.
- No rigorous public write-up found of image or video generation tooling inside Claude Code workflows; available material is vendor announcements and directory listings.
- Whether fal's MCP `get_pricing` returns an estimate for a specific request or only list prices was not stated.

## 5. Context management and failure modes

### Takeaway
The documented failure chain is: long always-loaded files reduce adherence; contradictions are resolved arbitrarily; too many or overlapping skill descriptions get truncated or mis-triggered; long sessions lose instructions to compaction and attention. Independent research supports the direction (performance falls as input and instruction count grow; context files add about 20% cost without improving task success on average), though the exact thresholds are not established for Claude Code. The documented remedies are pruning by a "would removing this cause mistakes" test, moving procedures to skills and guarantees to hooks, clearing context between tasks, and isolating parallel work in worktrees with explicit handoff artifacts.

### Cited Findings

**Long instruction files (official)**
- "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." "Claude may start 'forgetting' earlier instructions or making more mistakes." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. If you emphasize many lines, none of them stands out." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- "The over-specified CLAUDE.md... Claude ignores half of it because important rules get lost in the noise. Fix: Ruthlessly prune." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- "Every line loads into every session for every engineer working in the repo, whether it's relevant to their task or not." "Keep CLAUDE.md under 200 lines, give it an owner, and review changes to it like code." — [Anthropic blog, "Steering Claude Code", 2026-06-18](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Context is "a finite resource with diminishing marginal returns"; aim for "the smallest possible set of high-signal tokens." — [Anthropic engineering, context engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**Conflicting and stale instructions (official)**
- Conflicts between files: "Claude may pick one arbitrarily"; user and project rules do not override each other. Review CLAUDE.md, nested files and rules "periodically to remove outdated or conflicting instructions"; `/doctor prompt-audit` automates the search. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- A user instruction can also compete with Claude Code's own built-in guidance (for example git and PR rules), which can be switched off with `includeGitInstructions`. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Skills: "Don't include information that will become outdated." — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

**Skill sprawl and overlap (official)**
- "Too much can fill up your context window, but it can also add noise that makes Claude less effective; skills may not trigger correctly, or Claude may lose track of your conventions." — [Claude Code docs: features overview](https://code.claude.com/docs/en/features-overview)
- With many skills, "Claude Code drops some descriptions to fit the listing's character budget, which removes the keywords Claude needs to match your request." `/skill-doctor` (v2.1.252+) reports each skill's cost and usage and "flags skills in the listing that have never been invoked"; "start with the ones that have the highest context cost." — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- At Anthropic, "it can be quite easy to create bad or redundant skills"; "every skill that is checked in also adds a little bit to the context of the model." — [Thariq Shihipar, mirror](https://gist.github.com/Danm72/467f6d6cd193d19c0042371866d53b75)

**Instructions lost late in a session (official)**
- "If Claude follows a skill in its first response and stops following it later": (a) a rule that must hold every time belongs in a hook, optionally in the skill's `hooks` frontmatter; (b) word guidance so it applies to the whole task ("Run the tests after every edit" not "Run the tests"); (c) after compaction "invoke the skill again to restore its full content... put the most important instructions near the top of SKILL.md." — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- Instructions given only in conversation disappear at compaction; add them to CLAUDE.md to persist. CLAUDE.md can also instruct compaction ("When compacting, always preserve the full list of modified files"). — [Claude Code docs: memory](https://code.claude.com/docs/en/memory); [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- "If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run `/clear`." "A clean session with a better prompt almost always outperforms a long session with accumulated corrections." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)

**Measured evidence (third-party research)**
- 18 models tested: performance "varies significantly as input length changes, even on simple tasks"; a single distractor lowers accuracy; on LongMemEval models did markedly better with ~300-token focused prompts than ~113K-token full prompts, and Claude models showed the largest gap, largely through abstention. — [Chroma, "Context Rot", Hong, Troynikov, Huber, 2025-07-14](https://www.trychroma.com/research/context-rot)
- IFScale: with 500 simultaneous keyword instructions, "even the best frontier models only achieve 68% accuracy"; models show a bias toward earlier instructions; 20 models, seven providers. — [Jaroslawicz et al., arXiv 2507.11538, 2025-07-15](https://arxiv.org/abs/2507.11538)
- AGENTS.md study: across agents and models, repository context files (LLM-generated and developer-written) generally did not improve task success while raising inference cost by over 20% on average; agents do follow the instructions; repository overviews do not help; the files are useful for specifying non-standard coding practices (abstract as paraphrased by the fetch tool). — [Gloaguen et al., arXiv 2602.11988, v3 2026-09-29](https://arxiv.org/abs/2602.11988)
- Skills going unused: in Vercel's evals the skill was never invoked in 56% of cases; instruction wording changed outcomes ("You MUST invoke the skill" made agents read docs first and miss project context). — [Vercel blog, 2026-01-27](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- Practitioner interpretation: frontier models follow "~150-200 instructions with reasonable consistency" and Claude Code's system prompt already uses "~50"; recommended root file "< 300 lines", HumanLayer's own under 60. — [HumanLayer, 2025-11-25](https://www.humanlayer.dev/blog/writing-a-good-claude-md)

**Multi-session work (official)**
- Options: subagents; agent view (`claude agents`, research preview); agent teams (experimental, off by default); dynamic workflows; projects (public beta). "Do the tasks touch the same files? Isolate the work with worktrees." Agent teams do not isolate teammates, "so partition the work so each teammate owns a different set of files." Cross-session messaging lets sessions "pass findings and status between themselves." — [Claude Code docs: run agents in parallel](https://code.claude.com/docs/en/agents)
- Writer/reviewer split: "A fresh context improves code review since Claude won't be biased toward code it just wrote." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- Handoff across context windows: an initializer session creates a feature list (JSON with a `passes` field that later sessions may only flip), a progress log, an `init.sh`, and git commits; each session starts by reading the git log and progress file and ends with a commit and progress update. Failure modes addressed: doing too much at once and declaring the work finished early. — [Anthropic engineering, "Effective harnesses for long-running agents", 2025-11-26](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Structured note-taking: the agent "regularly writes notes persisted to memory outside of the context window" (for example a NOTES.md); sub-agents return condensed summaries, "often 1,000-2,000 tokens." — [Anthropic engineering, context engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Self-contained specs: "name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step"; execute in a fresh session. — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- Always-loaded content for this project should be the things every session needs regardless of task: where state lives (`pipeline-state.json`), the commands, the five or six non-obvious hazards, and a compact index of what exists and when to open it. The shipped-feature changelog, palette values (already in palette.json), template family counts and register descriptions are on-demand material by the docs' own tests ("derivable from the codebase", "changes frequently").
- The session listing shows overlapping entry points for the same job (project skill `script-audit`, synced `anthropic-skills:script-audit`, command `audit-script`, subagent `script-reviewer`; similar duplication for about ten other skills). The docs' overlap warning applies, and the duplicates also consume the shared 1% listing budget. `skillOverrides` (`off` or `name-only`) for the synced copies is the documented fix that does not require editing files.
- 47 doctrine documents in `project/` are safe from a context standpoint (zero cost until read) but exposed to the stale and conflicting failure mode, since nothing checks them. The cheapest documented control is `/doctor prompt-audit` for instruction files and, for doctrine that has become code (registers, transition grammar), a pointer to the lint or schema as the authority.
- For several agents editing one repo, the documented pattern is worktrees plus one small shared state artifact that only moves in defined ways (the harness post's `passes` field). `episodes/pipeline-state.json` validated by `pipeline_validator.py` already plays that role; hand-wired manifests marked `"handWired": true` are an example of protecting a shared file in code, not prose.
- HumanLayer reported in Nov 2025 that CLAUDE.md is wrapped in a reminder saying the context "may or may not be relevant." In this research session (Oct 2026) the project instructions arrived with wording that told the agent to adhere to them and that they override default behaviour. The wrapper wording therefore appears to differ by version or surface; third-party claims about it should be treated as dated.

### Gaps
- No Anthropic-published measurement of adherence versus CLAUDE.md length, or of trigger accuracy versus number of skills.
- IFScale and Context Rot predate current Claude models and do not test Claude Code's harness; they support the direction, not specific thresholds.
- No official guidance found on a shared "handoff note" file format for parallel human-run sessions beyond cross-session messaging and the long-running-harness artifacts.

## 6. Evaluation

### Takeaway
Three official tools exist as of October 2026: the skill-creator plugin (in-conversation with/without comparison and description tuning), `claude plugin eval` (CLI suite with graders, no-plugin baseline, CI exit codes; v2.1.269+, with early-access gating implied), and usage telemetry (`/skill-doctor`, `/doctor`). The documented starting size is small (two or three realistic prompts per skill, run with and without it), and Anthropic's own skill-creator says subjective skills are better judged by human review than by quantitative evals. For a solo creator the proportionate level is usage-driven: check that a skill triggers and helps on a few real prompts when it is created or changed, and let lints carry the regression load.

### Cited Findings

**Official tooling**
- "Seeing a skill trigger tells you Claude found it, not that it did what you intended... measure separately whether Claude invokes it on the prompts it should, and whether the output matches what you expect." Method: "Collect a few realistic prompts, run each one in a fresh session with the skill available and again with it turned off... A fresh session matters because leftover context from authoring the skill will mask gaps." The skill-creator plugin (`/plugin install skill-creator@claude-plugins-official`) automates test cases in `evals/evals.json`, isolated subagent runs, grading, benchmarks, blind A/B and description tuning. — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- `claude plugin eval`: requires Claude Code v2.1.269+ and "a plugin directory with a plugin.json... or a skills-directory plugin." Each case is a prompt plus graders; each case "runs three times by default"; runs are repeated with no plugin loaded to give `WITH`, `W/OUT` and `Δ`. Six grader types including `regex`, `tool_used`, `tool_order`, `file_exists`, `llm` (two of three judge votes) and `baseline`. `--threshold` defaults to 1.0; exit code drives CI. `claude plugin eval init` drafts the suite interactively. "Every eval run and every judge grader is a real model call on your account." — [Claude Code docs: plugin evals](https://code.claude.com/docs/en/plugin-evals)
- "The most common first finding is a Δ near zero with the case's `tool_used: Skill` grader failing, which means Claude isn't choosing your skill on natural phrasing." An `llm` judge can be shown a PNG, JPEG, GIF or WebP file produced by the run as an image. skill-creator and plugin eval use different case formats "and neither tool reads the other's case files." The page's troubleshooting includes entries titled "plugin eval is currently in early access" and "plugin eval is currently unavailable." — [Claude Code docs: plugin evals](https://code.claude.com/docs/en/plugin-evals)
- `claude plugin validate .claude/skills` (v2.1.233+) finds SKILL.md files whose frontmatter does not parse. — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- Usage: `/skill-doctor` shows per-skill cost and invocation counts; `/doctor` "recommends disabling the ones that were not used"; `/usage` attributes usage share to skills, subagents, plugins and MCP servers. — [Claude Code docs: measure plugin cost](https://code.claude.com/docs/en/plugins/measure)
- Anthropic logs skill usage internally with a PreToolUse hook to find popular skills and ones that undertrigger. — [Thariq Shihipar, mirror](https://gist.github.com/Danm72/467f6d6cd193d19c0042371866d53b75)

**Official method and sizing**
- "Start with 2-3 test cases. Don't over-invest before you've seen your first round of results." Run each with the skill and without (or against the previous version); add assertions only after seeing first outputs; "Not everything needs an assertion. Some qualities — writing style, visual design, whether the output 'feels right' — are hard to decompose into pass/fail checks. These are better caught during human review." Stop "when you're satisfied with the results, feedback is consistently empty, or you're no longer seeing meaningful improvement." — [agentskills.io evaluating skills](https://agentskills.io/skill-creation/evaluating-skills)
- "Remove or replace assertions that always pass in both configurations." "If pass rates plateau despite adding more rules, the skill may be over-constrained — try removing instructions." — [agentskills.io evaluating skills](https://agentskills.io/skill-creation/evaluating-skills)
- Trigger testing: about 20 queries (8–10 should trigger, 8–10 near-miss should not), three runs each, pass at trigger rate above 0.5, 60/40 train/validation split, "five iterations is usually enough." — [agentskills.io optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)
- skill-creator: if the user wants to "just vibe", skip formal evaluation; skills with "objectively verifiable outputs (file transforms, data extraction, code generation, fixed workflow steps)" benefit from test cases, while subjective skills (writing style, art) "often don't need" quantitative evals. — [anthropics/skills skill-creator SKILL.md](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- Platform checklist: "At least three evaluations created"; that page also states "There is not currently a built-in way to run these evaluations," which the Claude Code docs above supersede for Claude Code. — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- General agent evals: "20-50 simple tasks drawn from real failures is a great start"; convert checks you already do manually; test both "where a behavior should occur and where it shouldn't"; "grade what the agent produced, not the path it took"; "You won't know if your graders are working well unless you read the transcripts"; code graders are fast and objective but brittle, model graders flexible but need calibration; no single layer catches everything (Swiss cheese model). — [Anthropic engineering, "Demystifying evals for AI agents", 2026-01-09](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Caution against over-checking: "A reviewer prompted to find gaps will usually report some, even when the work is sound... Chasing every finding leads to over-engineering: extra abstraction layers, defensive code, and tests for cases that can't happen." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)

**Third-party practice**
- "Start with error analysis, not infrastructure." "Spend 30 minutes manually reviewing 20-50 LLM outputs whenever you make significant changes." "Focus automated evaluators on failures that persist after fixing your prompts." Binary pass/fail over rating scales; generic off-the-shelf metrics "waste time and create false confidence." — [Hamel Husain and Shreya Shankar, evals FAQ (page date as retrieved: September 2026; first publication date not verified)](https://hamel.dev/blog/posts/evals-faq/)
- Vercel built evals around APIs absent from training data and reran to rule out variance; their headline finding (skill unused in 56% of cases) came from a trigger check, not an output-quality check. — [Vercel blog, 2026-01-27](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- Opposite pressure: the AGENTS.md study concludes that any attempt to improve agent performance with context files should be rigorously evaluated before deployment. — [Gloaguen et al., arXiv 2602.11988](https://arxiv.org/abs/2602.11988)

### Inferences
- A proportionate standard for a solo creator, assembled from the sources: (1) for each new or materially changed skill, two or three real prompts from actual episode work, run fresh with and without it, outputs read by the creator; (2) a trigger check only for skills meant to auto-trigger, since user-invoked skills (`disable-model-invocation: true`) have nothing to measure; (3) anything mechanically checkable goes into an existing lint, which then serves as the regression suite at no model cost; (4) a monthly glance at `/skill-doctor` to retire unused skills. This stays within the "2-3 test cases" starting point and the skill-creator's "subjective skills need human review" position.
- The full description-optimization loop (20 queries × 3 runs, five iterations) is roughly 300 model sessions per skill. It is disproportionate for 25 skills in a pipeline where the creator invokes most skills by name; it is worth running only on the one or two skills that must fire unprompted (for example a picture-technique lookup).
- Picture work is the subjective case the guidance carves out. The existing practice of rendering stills and reading them is the human-review layer; the `llm` grader's image support in `claude plugin eval` exists if an automated visual check is ever wanted, but nothing in the sources argues it is needed at this scale.
- Given the project's recorded history of over-testing, the official caution about adversarial reviewers applies to persona and audit skills too: findings from a skill asked to find problems are not evidence the work is wrong.

### Gaps
- Not confirmed: whether a plain `.claude/skills/` project directory counts as a "skills-directory plugin" for `claude plugin eval` without a manifest, and whether the command is generally available or still gated to early-access accounts in October 2026.
- No published guidance found that sizes evaluation specifically for solo or non-engineering creative pipelines.
- No write-ups on skills or agent evals by Eugene Yan or Geoffrey Litt were retrieved in this pass.

## 7. Promotion path

### Takeaway
Anthropic documents the promotion path as a set of triggers, not a pipeline: a correction repeated twice becomes a CLAUDE.md line; a procedure pasted three times becomes a skill; something that must happen every time becomes a hook; setup needed in a second repo becomes a plugin. Auto memory sits before all of these as Claude's own notes (preferences, corrections, non-derivable project facts), with a stated exclusion for anything derivable from the code or already in CLAUDE.md. The reverse direction is also documented: when Claude already behaves correctly, delete the line or convert it to a hook.

### Cited Findings
- The trigger table: "Claude gets a convention or command wrong twice → add it to CLAUDE.md"; "You keep typing the same prompt to start a task → save it as a user-invocable skill"; "You paste the same playbook or multi-step procedure into chat for the third time → capture it as a skill"; "A side task floods your conversation → route it through a subagent"; "You want something to happen every time without asking → write a hook"; "A second repository needs the same setup → package it as a plugin." "A repeated mistake or a recurring review comment is a CLAUDE.md edit, not a one-off correction in chat." — [Claude Code docs: features overview](https://code.claude.com/docs/en/features-overview)
- When to add to CLAUDE.md: Claude "makes the same mistake a second time"; "a code review catches something Claude should have known"; "you type the same correction... that you typed last session"; "a new teammate would need the same context." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Memory versus CLAUDE.md: CLAUDE.md is written by you and holds "instructions and rules"; auto memory is written by Claude and holds "learnings and patterns"; "Use CLAUDE.md files when you want to guide Claude's behavior." Auto memory records `project` items as "ongoing work, deadlines, and decisions that Claude can't derive from the code or git history" and skips what CLAUDE.md already says. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Conversation to skill: "Complete a task without a Skill... Notice what information you repeatedly provide"; then "Ask Claude A to create a Skill that captures this... pattern"; "Review for conciseness"; test with a fresh instance; "Iterate based on observation." — [Anthropic platform docs: best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Artifacts to skill: "A data-pipeline skill synthesized from your team's actual incident reports and runbooks will outperform one synthesized from a generic 'best practices' article"; good sources include internal docs, schemas, review comments, version-control history and "real-world failure cases and their resolutions." A pitfall is generating a skill from the model's general knowledge with no project material. — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Skill to script: "If you notice the agent independently reinventing the same logic each run — building charts, parsing a specific format, validating output — that's a signal to write a tested script once and bundle it in `scripts/`." — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Skill instruction to hook: a rule Claude skipped "that must hold every time: move the rule into a hook." — [Claude Code docs: skills](https://code.claude.com/docs/en/skills)
- Demotion: "If Claude already does something correctly without the instruction, delete it or convert it to a hook." "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- Gotchas as the incremental channel: start with an empty gotchas section and add an entry each time Claude goes wrong; it is "the highest-signal content." — [Thariq Shihipar, mirror](https://gist.github.com/Danm72/467f6d6cd193d19c0042371866d53b75); [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Long-term direction: Anthropic's stated goal is to let agents "create, edit, and evaluate skills on their own, codifying their behaviors into reusable capabilities." — [Anthropic engineering, Agent Skills post, 2025-10-16](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Decision and progress records for later sessions: progress log, feature list with pass state, descriptive git commits, read at the start of every session. — [Anthropic engineering, long-running harnesses, 2025-11-26](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

### Inferences
- A ladder consistent with the sources, lowest cost first: (0) conversation or experiment; (1) research note or analysis file in the repo (zero context cost, found by grep, dated so staleness is visible); (2) a pointer to it from the relevant skill with a "read this when" condition, or a gotcha line in the skill if it corrects a mistake; (3) an entry in a structured catalogue or registry if it is a reusable fact with fields; (4) a script if the agent keeps rebuilding the same logic; (5) a lint, schema constraint or hook if it must hold every time. Promotion upward is triggered by recurrence (twice for a correction, three times for a procedure), not by importance.
- What belongs in each store for this project: auto memory holds working preferences and current focus (it already holds "skip over-testing" and the focus shift, which are correct uses); CLAUDE.md holds facts true in every session; decisions with rationale belong in `project/DECISIONS.md` (on-demand), because auto memory is machine-local and not shared with cloud sessions or other machines.
- The newly produced material maps as: the ~70 picture techniques → catalogue data plus generated doc plus one lookup-oriented skill; the fal.ai generation and edit scripts → `tools/` scripts with `--help`, `--dry-run` and sidecars, referenced from the asset skills as "run exactly this"; research notes → stay as dated notes, linked from the skill that needs them; new production rules → split by the mechanical/judgment test into lint rules and skill gotchas, with at most a handful reaching CLAUDE.md.
- The project's `publish-retro` skill writing validated rules into `EDITORIAL_PLAYBOOK.md` is a promotion mechanism of the documented kind; at 467 lines and 69KB the playbook is itself now a candidate for the same split (mechanical rules to lint, the rest indexed by stage).

### Gaps
- No Anthropic document presents a single named "notes → doc → skill → lint" pipeline; the ladder above is synthesized from separate trigger statements.
- No official guidance found on writing decision records specifically for agents (format, placement), beyond the `project` memory type and the harness post's progress files.
- How auto memory should be reconciled with repo docs over time (for example, promoting a memory into CLAUDE.md) is not described beyond "ask Claude to add this to CLAUDE.md"; the session's skill list includes a `consolidate-memory` skill whose behaviour I did not examine.

## 8. Worked examples

### Takeaway
Public examples show three working shapes for domain knowledge: a small inline style skill (Anthropic's brand-guidelines, about 70 lines, values listed inline); a workflow skill with phase-gated reference files (Anthropic's mcp-builder); and a rule catalogue with one file per rule, a short index SKILL.md and a generated compiled document (Vercel's react-best-practices). Reports of what works are mostly qualitative; the two quantitative data points are Vercel's (an always-loaded compressed index beat an on-demand skill) and SkillsBench's (focused skills beat exhaustive ones).

### Cited Findings
- anthropics/skills: "skills that demonstrate what's possible with Claude's skills system", "for demonstration and educational purposes only"; about 180K stars as retrieved; installable as a Claude Code plugin marketplace (`/plugin marketplace add anthropics/skills`). The `skills/` directory lists 19 entries including `brand-guidelines`, `frontend-design`, `theme-factory`, `canvas-design`, `algorithmic-art`, `mcp-builder`, `skill-creator`, `webapp-testing`, `docx`, `pdf`, `pptx`, `xlsx`. — [anthropics/skills](https://github.com/anthropics/skills)
- brand-guidelines: about 70 lines; colours as a bulleted list with inline hex values (for example Dark `#141413`, Orange `#d97757`), typography as two lines (Poppins headings, Lora body, with fallbacks), then behaviours (heading size threshold, accent cycling). No reference files or scripts. — [anthropics/skills brand-guidelines SKILL.md](https://github.com/anthropics/skills/blob/main/skills/brand-guidelines/SKILL.md)
- frontend-design: about 120 lines of prose with a persona, design principles, a plan/review/build/critique loop, named anti-patterns (a calibration list of common AI-design clichés) and a few concrete thresholds ("less than 80 characters" per line, "4–6 named hex values"); no tables, no reference files. — [anthropics/skills frontend-design SKILL.md](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)
- mcp-builder: about 170 lines, four phases; four reference files each tied to a phase (`reference/mcp_best_practices.md` labelled "Load First"; language guides for phases 1.3 and 2; `reference/evaluation.md` for phase 4); the final phase requires 10 evaluation questions in an XML file. — [anthropics/skills mcp-builder SKILL.md](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/SKILL.md)
- skill-creator: itself the reference implementation of the eval loop (evals.json, with/without subagent runs, benchmark, review viewer, description optimizer). — [anthropics/skills skill-creator SKILL.md](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- Vercel react-best-practices: SKILL.md of about 170 lines is an index: a priority table of eight categories (CRITICAL to LOW) with filename prefixes, a quick-reference list of rule IDs with one-line summaries, then "Read individual rule files for detailed explanations and code examples" (`rules/async-parallel.md`) and "For the complete guide with all rules expanded: `AGENTS.md`." Each rule file has frontmatter (`title`, `impact`, `tags`) and incorrect/correct examples; build, validate and test-extraction scripts generate AGENTS.md and `test-cases.json`. — [vercel-labs/agent-skills react-best-practices](https://github.com/vercel-labs/agent-skills/tree/main/skills/react-best-practices)
- Vercel docs index: an 8KB pipe-delimited index of documentation paths placed in AGENTS.md reached 100% on their evals where the on-demand skill reached 53% (default) and 79% (with explicit instructions); they recommend skills for vertical, action-specific workflows that users trigger explicitly, and passive context for general framework knowledge. — [Vercel blog, 2026-01-27](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- Anthropic internal practice: library/API reference skills (including a frontend-design skill for a design system) "often included a folder of reference code snippets and a list of gotchas"; skills are checked into the repo for small teams and moved to a plugin marketplace at larger scale; skills can reference each other by name. — [Thariq Shihipar, mirror](https://gist.github.com/Danm72/467f6d6cd193d19c0042371866d53b75)
- A community design-system skill keeps the full spec in a root `DESIGN.md` and a short `SKILL.md` whose checklist has Claude identify which component sections it needs before writing code. Qualitative report only. — [Medium, gravitano](https://medium.com/@gravitano/i-built-a-claude-code-skill-that-turns-a-design-system-into-pixel-perfect-ui-heres-how-6d00c90daccd)
- Simon Willison's sketch of a "data journalism agent" as "a folder full of Markdown files and maybe a couple of example Python scripts" is the general template for a domain kit. — [Simon Willison, 2025-10-16](https://simonwillison.net/2025/Oct/16/claude-skills/)

### Inferences
- The three shapes map onto the project's material. Palette and type rules resemble brand-guidelines, but the project already does better by keeping values in `palette.json` with lint rules; the skill should point to the file, not restate hex codes. Multi-stage production skills (visual-spec at 1,013 lines) resemble mcp-builder and would follow its pattern by moving per-family detail into reference files tied to named steps. The picture-technique catalogue resembles react-best-practices: per-entry records with frontmatter-like fields (family, when to use, cost, tool, failure modes), an index ordered by priority, and a generated compiled document.
- The impact-level field in Vercel's rule files is a transferable idea for a technique catalogue: an explicit priority or "reach for this first" field gives the agent a default ordering, which matches the "defaults, not menus" guidance.
- Anthropic's own example design skills are short and opinionated and carry no catalogue at all; none of the public examples reviewed embeds 70 entries in a SKILL.md body.

### Gaps
- No public post-mortem found that reports measured results for a design-system, brand or component-library skill (trigger rates, adherence, before/after quality); available write-ups are descriptive.
- I did not review "awesome" lists of skills in detail; the listicles surfaced by search were not primary sources and are not relied on here.
- The rule count in Vercel's react-best-practices and any published results from its extracted test cases were not stated on the pages retrieved.
